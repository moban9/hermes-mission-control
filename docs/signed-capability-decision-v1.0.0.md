## Established source facts

- `server/discord.py:49–55` `_decision_url` creates an approval link whose `sig` query parameter is an HMAC bearer capability. The notification sends both decision links externally (`86–90`). Never print a capability value in reports, tests, logs, examples or evidence.
- `server/signing.py:31–41` signs request identifier plus decision only. It does **not** bind an expiry, nonce, viewer identity, browser session or HTTP method. Verification is a constant-time equality check with a configured key. Current 'Invalid or expired' UI wording is not evidence of expiry enforcement.
- `GET /v1/approvals/{identifier}/decide` validates the capability and renders a confirmation form; it does not mutate approval state. The capability is included in a hidden form field (`app.py:661–696`). `POST` to that same path validates it and applies the decision (`699–731`). Anyone possessing the valid capability has that scoped authority, regardless of whether they hold a guest viewer token. Already-decided DB state prevents a second effective transition but is not a time limit on a still-pending capability.
- The existing alternative write path is owner-authenticated `POST /v1/approvals/{identifier}` (`614–638`); a guest viewer principal is rejected by `_require_owner`. Do not confuse it with the distinct signed POST despite the duplicate Python function name.
- `_auth` also accepts viewer authentication via query, ahead of bearer-header fallback (`app.py:84–99`). Dashboard `tokenQuery`, fetches and EventSource use query authentication. This is an additional credential-in-request-URL channel, not solved merely by retiring approval links.
- The signed confirmation/result paths currently lack safe scrub-then-HTML-escape boundaries. Signed route URLs do not match the `.html` no-store branch of middleware; its generic fallback is `Cache-Control: no-cache`, not `no-store`. No explicit `Referrer-Policy` is installed in the inspected app. Proxy/browser/Discord logging configuration has not been verified. `urllib.request.urlopen` in `discord._post` has default redirect behavior; raw exception diagnostics are printed. No claim is made that all redirects actually forward credentials; preventing that forwarding must be tested.

## Can leakage be closed inside the approved architecture?

**Not completely under the literal zero-secret-in-served-URL requirement.** A usable bearer capability embedded in a link is authority exposed to the link recipient, notification service and URL handling chain by construction. It cannot simultaneously remain a working capability URL and be absent from all served URLs. Redacting its signature would disable the approved flow. HMAC unforgeability does not make possession non-secret.

Accidental secondary leakage can be reduced substantially while retaining the architecture: short-lived identifier-and-decision-scoped capability use, rejecting after expiry/decision; no raw query/body credentials in application, ingress, proxy, tracing or outbound exception logs; no-store on confirmation/result/error responses; `Referrer-Policy: no-referrer`; avoid third-party assets/navigation from capability pages; scrub then context-correct HTML/attribute escape for free text; reject credential-bearing or cross-origin redirects and never forward authentication headers/query capabilities. Reject unsafe dashboard/notifier target configuration, and test redirect chains. Any addition of expiry must preserve scope, handle outstanding-link compatibility explicitly, and stay within the approved implementation authorization; this brief does not approve changing the signed format or silently invalidating outstanding links.

These measures do not erase existing notifications, browser history, URL copies, endpoint access by the intended recipient, or all upstream request logs. Therefore they cannot support a literal 'no secrets in served URLs' statement. No proxy or application-header setting can prove deletion from every external recipient. Continue independent redaction/escaping/tests where authorized; keep this acceptance gate unresolved rather than claim completion.
