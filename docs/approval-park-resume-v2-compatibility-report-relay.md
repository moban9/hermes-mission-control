# Approval park/resume v2 compatibility gate — Relay

**Verdict: NOT SUPPORTED / BLOCKED for v2 build on the installed public surface inspected.** The documented API admission path is usable in principle, but does not itself deterministically start the CEO run before LLM execution, nor does it park/unblock a canonical board card. This is a capability finding, not feature acceptance, deployment approval, or operational closure. No source/hook/configuration changes or runtime mutations were made.

## Installed interface findings

### Supported, bounded

- Existing MC plugin registers public hooks `pre_llm_call`, `pre_api_request`, `post_api_request`, `pre_tool_call`, `post_tool_call` via `ctx.register_hook(name, callback)`. The documented/observed block mechanism is a `pre_tool_call` return envelope `{"action":"block","message":...}`. Current plugin manifest advertises only those five hooks. No finalization, worker-exit, session-start or board lifecycle hook appears in the inspected manifest/plugin implementation.
- Official API-server docs specify `POST /v1/runs`, with fields including `input` and optional `session_id`, `instructions`, `conversation_history` or `previous_response_id`; `Idempotency-Key` is accepted for safely retryable admission. Docs describe durable reservation/admission and a `run_id`, not synchronous execution or LLM start. An HTTP 202/admission response is therefore not evidence of `ceo_started_at` or a dispatcher wake callback.
- The docs explicitly reject a `session_id` owned by CLI/TUI/Desktop/ACP/messaging with HTTP 409 `permission_denied` before admission. Thus the proposed bridge must bootstrap and target a distinct API-owned approval-control session under the existing CEO/default profile. No session identifier, API server endpoint/key, capability response or config was probed; no guessed values are supplied.

### Required capabilities missing / not proven

1. **Deterministic park/finalization:** no supported installed public API was identified to ensure canonical `kanban_block(kind="needs_input", ...)` after a gated tool is blocked, including when the model halts, and verify worker exit. `pre_tool_call` can block a tool only; relying on a model to remember a subsequent action fails the contract. Exact public park method/signature: **none found**.
2. **Park acknowledgement and lifecycle recovery:** no supported plugin session-start or worker-exit callback found in the manifest or inspected installed plugin. Consequently there is no verified canonical block generation or originating profile/session/run recovery callback. Exact public callback/signature: **none found**.
3. **Canonical CAS-unblock and immediate dispatcher signal:** no supported public board method was found that conditionally clears only the matching `needs_input` block generation and signals dispatch immediately. Raw SQLite/private internals are expressly disallowed, so no substitute was attempted. Exact public method/signature: **none found**.
4. **Deterministic wake-before-model:** public `POST /v1/runs` is admission only. No installed callback/API identified that ties the approval event to immediate run start, and records actual session-start, before the LLM handles the event. The required `ceo_started_at` within 5s and card unblock/dispatch event were not reproduced. The installed `/v1/capabilities` response and `run_submission` capability were not tested; cannot claim support based on latest docs.
5. **Scoped grant injection:** installed manifest/plugin has no session-start hook or scoped plugin runtime state channel. Existing middleware documentation says middleware fails open on exceptions; it cannot act as this gate. No supported means was found to deliver grant into protected plugin/session runtime memory while keeping it out of model args/history, logs and SSE. Exact callback/signature: **none found**.
6. **Identity/bootstrap:** the intended design needs three distinct principals: originating plugin/runtime scoped to its profile/board; owner principal for decision; internal bridge principal for wake receipts/reconciliation. Proposed MC OpenAPI distinguishes `pluginAuth`, `ownerAuth`, and `bridgeAuth`, but these are proposed schemas, not installed routes. Existing `API_SERVER_KEY` must stay separate from the MC plugin, owner and bridge credentials; grant-signing secret must be independent of all of them. No credential values were inspected. A CEO API-owned control session and authorized API endpoint/key/config activation need an approved bootstrap procedure and identity proof; none was exercised.

## Proposed contract interface inventory (not installed API claims)

The v2 OpenAPI file is an application proposal, OpenAPI 3.1.0, info version 2.0.0. It declares seven MC paths: `POST /v2/approvals/requests`, `POST /v2/approvals/{id}/parked`, `POST /v2/approvals/{id}/decisions`, `POST /v2/approvals/{id}/grant`, `POST /v2/approvals/{id}/consume`, `POST /v2/approvals/wake-receipts`, `GET /v2/approvals/reconcile`. These are not live/installed endpoints. Their security scheme names are proposed bearer scopes `pluginAuth`, `ownerAuth`, `bridgeAuth`; no signatures beyond HTTP operation/method and JSON schemas are available yet.

The only external transport selected by the design that is grounded in official public docs is Hermes API server `POST /v1/runs` with an API-owned session, API key auth and stable `Idempotency-Key`. Documentation proves admission/idempotency and the foreign-session 409 restriction, not deterministic start, board transition or grant injection. Do not interpret admission HTTP 202 as wake.

## Gate and requested next step

**Block v2 implementation pending capability/permission resolution.** Need a supported installed API/runtime surface (with exact names/signatures and authorized bootstrap) for: (a) deterministic post-hook park plus worker-exit/session-start recovery; (b) generation-conditional canonical unblock plus immediate dispatcher signal; (c) deterministic API-run start acknowledgement; and (d) scoped session-start grant delivery to plugin memory. Then reproduce the lifecycle in an isolated harness. Do not write raw board DB state, use private imports, add dependencies, alter shared config/restart/sync profiles, or deploy as a workaround.
